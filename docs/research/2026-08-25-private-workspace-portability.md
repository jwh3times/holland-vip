# Private workspace portability for a public repository

Date: 2026-08-25

## Conclusion

Use a **separate private GitHub companion repository** as the durable source of truth for private Markdown, use that repository's **private Issues** for actionable work state, and optionally put those issues in a **private GitHub Project** for a dashboard. Reserve security advisories in the public repository for genuine vulnerabilities under coordinated disclosure. Use OneDrive as a secondary recovery copy, not as the only record.

This preserves the public/private boundary while making the working context available from any authenticated computer. It also keeps prose in ordinary Git, where cloning provides complete file history and offline use, while using Issues for the task-tracking job they are designed to do.

## Recommended ownership model

- **Public `holland-vip` repository:** code; public architecture, setup, and contributor documentation; generated artifacts only when the project requires them; no private notes.
- **Private companion repository:** private Markdown, decision records, research notes, session handoffs, and security notes that are not genuine repository vulnerability advisories.
- **Private companion Issues:** tasks, private bugs, follow-ups, and resumable work state. Keep an intentionally short committed handoff file such as `CURRENT.md` for the context a fresh clone needs before browsing Issues.
- **Private Project:** optional aggregate dashboard over companion-repository Issues. Do not use public-repository Issues or Project-only draft items for confidential text.
- **Public repository security advisories:** only genuine security findings that need private remediation followed by coordinated disclosure.
- **Independent recovery:** occasionally copy or export the private companion repository outside GitHub, such as to OneDrive Personal Vault. Store GitHub recovery codes and any encryption keys in a password manager or other independent protected location; GitHub recommends multiple recovery methods and secure recovery-code storage. [GitHub 2FA recovery guidance](https://docs.github.com/en/authentication/securing-your-account-with-two-factor-authentication-2fa/configuring-two-factor-authentication-recovery-methods)

On a new computer, authenticate to GitHub and clone the public and private repositories as siblings. If revealing the companion repository's name is harmless, a sanitized public bootstrap note can name it. If its existence or name is itself sensitive, keep that single locator in the password manager or Personal Vault instead. Do not embed the private repository as a submodule of the public one unless exposing its URL and name is acceptable.

For this repository specifically, an alternative that preserves the existing `private/` convention is to clone the companion repository into the already ignored `private/` directory as an independent nested repository, not a submodule. This keeps agent paths stable and prevents the public repository from recording the private remote URL. A bootstrap note should make the second clone step explicit.

## Why this is the recommended tradeoff

The companion-repository pattern has the fewest unusual failure modes. It uses GitHub's actual private access control instead of relying on an unguessable URL or perfect encryption discipline; it preserves Markdown as portable, reviewable files; and it separates durable knowledge from task state without losing the ability to organize both in GitHub. OneDrive then provides provider diversity for recovery, while advisories retain their narrow security-disclosure purpose.
